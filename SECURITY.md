# Security boundaries

This experimental prototype has not received an independent cryptographic or application security audit. Do not infer a secure messaging protocol from the use of an established cipher.

## Trusted setup

The creator generates 32 random bytes with the browser's `crypto.getRandomValues`. Both people use that exact key for AES-GCM messages. Version 0.4 encrypts the saved key with a passphrase-derived wrapping key. There is no global shared key, public-key exchange, key server or recovery service.

Version 0.4's private HTML stores only an authenticated encrypted envelope in an inert metadata field. Native PBKDF2-HMAC-SHA-256 at 600,000 iterations and a fresh random 16-byte salt derive an AES-256-GCM wrapping key; the wrap has a fresh random 12-byte nonce and full 16-byte tag. All envelope parameters are authenticated and checked against fixed supported values before derivation. See [KEY-STORAGE.md](docs/KEY-STORAGE.md) for the exact format, normalization, cost rationale and bounds.

Both people receive the same authentic file and passphrase through private trusted handover, keeping the passphrase separate when sending the file. Someone holding the file can guess passphrases offline without any UI attempt limit. A long unpredictable passphrase matters; the 16-character creation minimum does not prove strength. PBKDF2 is native and portable here, but is not memory-hard. Anyone holding both file and passphrase can decrypt past/future traffic and forge either participant's messages. A helper who creates the file knows its passphrase. There is no reset or recovery. Downloads, backups and cloud sync may retain copies.

There is no fingerprint comparison or confirmation screen. Trust rests on handing over the correct, unmodified private file through that external trusted channel. The encrypted envelope authenticates the wrapped key and parameters, not the HTML program. A modified HTML file can modify the code and CSP. The generic starter contains an empty metadata slot; each new setup generates a fresh independent random key. Use the same downloaded file for both members of one conversation, and a new file for a different conversation.

Old BPP1 codes and unprotected private HTML files are retained as migration inputs. The starter validates the code/checksum and wraps that exact original key. HTML is size-bounded and read only as text; its known metadata is extracted without parsing/executing a document or loading resources. Old plaintext files/codes remain fully capable of reading and forging messages. **Saving a protected copy cannot revoke or repair an exposed old key.** Keep remaining plaintext copies safe or delete them/backups; deletion is not guaranteed. Authentic distribution and key quality still depend on a trusted generator and handover.

Generate separate conversation files for separate peers. The checksum cannot prove randomness: someone could manufacture a valid legacy code with a weak key. Use keys generated by a trusted, unmodified copy of the starter.

## Cryptography and integrity

The browser implements AES-256-GCM; this project does not implement a cipher. Each encryption uses a new 12-byte random nonce. The five-byte protocol header is authenticated as additional data, with a full 16-byte tag. Failed authentication releases no plaintext to the UI.

Both peers use the same key. Either can decrypt or create any pair message. There is no sender signature, direction binding, replay detection, timestamp validation, forward secrecy, post-compromise security, ratchet, length-hiding padding, or denial-of-service guarantee. Captured valid messages can be replayed indefinitely. A code compromise exposes recorded and future traffic using that key.

Random nonces have a nonzero collision probability. This is a small-volume manual prototype, not a high-volume protocol. There is no persistent pair-wide message counter or automatic key rotation. Restarting does not rotate a reused key. Production use needs explicit lifecycle/volume limits and independent review.

Theme, reply act and encoded packet length are public. In v2, fixed byte packing can shorten Persian UTF-8 before encryption, so exposed size is packed size, not necessarily original size. It is not length hiding. Packing has no shared or adaptive dictionary. Cover wording that normalizes to the same encoded bytes, including the two openings for one profile, is intentionally equivalent; literal punctuation and spacing are not authenticated. The decoded version/profile header, nonce and encrypted payload are protected by GCM verification. Unpacking happens only after authentication and is bounded to 2,048 output bytes.

## On-device handling

Imported `CryptoKey` objects are non-extractable. Raw key/password byte buffers are overwritten after import or use where practical. **The deliberate private-file download is persistent encrypted key storage.** Non-extractability alone is not at-rest protection; password wrapping supplies that boundary. Closing, reloading or Done does not remove downloaded files or revoke copies. Loss has no recovery path; key/passphrase leakage requires a new conversation and private handover, and cannot protect old traffic.

No application code writes secrets/messages/context to localStorage, sessionStorage, IndexedDB, cookies, logs, network requests or URL text. A blob URL references the deliberate download in browser memory. No passphrase, raw key, setup code or message enters new exported files. Exports use an immutable build-time UI shell and original bootstrap script, never live form/result DOM. Only a strictly validated `BPK1-[0-9A-F]{174}` encrypted envelope is substituted in inert metadata. It is not interpolated into executable script, CSS or a URL. The nested shell stays key-free. CSP hashes do not change in private copies.

Done clears draft, received cover, decoded plaintext, outgoing cover and reply context while retaining the runtime key. Ordinary focus/visibility changes, such as switching to a messenger, retain unlock. Actual navigation/pagehide drops the key, clears sensitive fields and invalidates pending work. Reload, reopen and back-forward-cache restoration require one passphrase unlock. There is no shared key/passphrase cache or timed lock. Pending crypto/clipboard results are invalidated when relevant inputs change; native derivation cannot be aborted, so stale results are discarded and one pending key operation is allowed at a time. Download retry offers identical encrypted content.

This is not guaranteed memory erasure: JavaScript strings, DOM values, browser recovery data, swap, crash dumps, extensions, input methods, accessibility software, OS screenshots, and clipboard history are outside the app's control. Non-extractability does not stop a compromised page from using a key. Copying plaintext may expose it to clipboard synchronization. Clearing the page does not clear the clipboard or downloaded files.

Do not use an untrusted HTML copy. Its content security policy blocks external resources and connections, permits only the bundled script/style hashes, and allows font data URLs for the embedded licensed WOFF2. `font-src data:` does not authorize remote font hosts; `connect-src 'none'` is unchanged. This is defense in depth, not a signature: someone modifying the file can modify the policy too. Verify distributions through a trusted channel. There is no automatic updater.

## Cover text

The grammar tables are public. Covers can be recognized, decoded to ciphertext, and statistically detected. Naturalness is best effort; uniform phrase choices are not modeled on real conversation frequencies. No claims of steganographic security, plausible deniability, censorship resistance, or undetectability are made. Six bounded themes, basic dialogue-act matching, and staged clause structures provide rough continuity only. They do not understand arbitrary questions or reliably interpret negation. Public context never comes from private-message text.

Messages are bounded to 2,048 bytes and cover inputs to 180,000 UTF-16 code units. Recognized copy/paste transformations are specified in [FORMAT.md](docs/FORMAT.md) and [FORMAT-V2.md](docs/FORMAT-V2.md). Unknown/missing words, invalid frames, unsupported versions, and failed tags raise explicit errors. There is no guessing or unauthenticated recovery mode.
